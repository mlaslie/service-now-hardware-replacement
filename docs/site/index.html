Gemini Enterprise · ServiceNow · Cloud Run

Hardware Replacement Agent

Employees report broken hardware in a sentence or a photo, from the Gemini Enterprise web or mobile app. The agent finds the device, checks it with them, files a ServiceNow ticket as that person, routes equipment to the team that fixes it, and answers "any update?" at any time.

The agent holds no ServiceNow credentials: each user signs in to ServiceNow through Gemini Enterprise, and every call uses their own token, so ServiceNow's permissions decide what they can do (measured role matrix).

Architecture

The pieces

  • Gemini Enterprise signs each user in to ServiceNow (OAuth authorization code) and forwards their token with every message.
  • Cloud Run runs the ADK agent behind an A2A server. Only Gemini Enterprise's service agent may call it.
  • The agent stays on Cloud Run because an A2A agent on Agent Runtime doesn't receive the user's credential (measured).

Install, step by step

About an hour. You need a Google Cloud project with billing (an Owner account is simplest), the gcloud CLI, uv, a Gemini Enterprise app you administer, and admin access to ServiceNow.

1Get the code

shell
git clone https://github.com/OWNER/service-now-hardware-replacement.git {REPO_DIR}
cd {REPO_DIR}
uv sync

2ServiceNow: sign-in client and roles

  1. OAuth client for Gemini Enterprise. In ServiceNow: System OAuth > Application Registry > New > Create an OAuth API endpoint for external clients. Keep it active, grant type authorization code, redirect URLs below. Copy the client ID into your values and keep the secret for step 7. Google's walkthrough of the same client: ServiceNow configuration. An existing Gemini Enterprise ServiceNow connector's client works too.
redirect URLs (one field, comma-separated)
https://vertexaisearch.cloud.google.com/console/oauth/default_oauth.html,https://vertexaisearch.cloud.google.com/oauth-redirect
  1. Requester roles. itil gives every feature; no roles works with limits; mind licensing. See ServiceNow roles.
  2. Optional, for demo data and the permission checker: a second client the same way, redirect URL http://localhost:8765/callback, stored in Secret Manager (Secret Manager quickstart):
shell · replace CLIENT_SECRET, and the ID if it's the second client
printf '%s' '{INSTANCE}|{CLIENT_ID}|CLIENT_SECRET' | gcloud secrets create servicenow-seed-oauth --data-file=- --project {PROJECT_ID}

3Settings: .env

Create .env in the repository folder with this content (built from your values). AGENT_ENGINE_ID is filled in by step 4.

.env
# Deployment settings; see docs/CONFIGURATION.md
GOOGLE_CLOUD_PROJECT={PROJECT_ID}
SN_INSTANCE_URL={INSTANCE}
AGENT_ENGINE_ID=
REGION={REGION}
SERVICE_NAME={SERVICE_NAME}

Or: cp .env.example .env and edit. Every variable: Configuration.

4Google Cloud setup (once)

shell
gcloud auth login
gcloud auth application-default login
gcloud config set project {PROJECT_ID}
./scripts/setup.sh

setup.sh is safe to rerun. It enables the APIs, creates the photo bucket, creates the service account hardware-agent (Vertex AI user, log writer, bucket object access), and creates the Agent Runtime instance that holds Sessions and Memory Bank, writing AGENT_ENGINE_ID into .env.

5Your organization profile

Edit config/organization.yaml (a hospital example) or start from the office example: agent name, button colour, problem choices, texts. Every field.

shell
# optional: start from the generic office profile
cp config/examples/office.yaml config/organization.yaml
uv run python -m app.profile

6Deploy

shell
./scripts/deploy.sh

Checks the profile, deploys from source to a private Cloud Run service, passes the settings as environment variables, and grants roles/run.invoker to Gemini Enterprise's service agent. Rerun after any code or configuration change.

7Register in Gemini Enterprise

Get the agent card:

shell
curl -s -H "Authorization: Bearer $(gcloud auth print-identity-token)" {SERVICE_URL}/.well-known/agent-card.json

Google Cloud console > Gemini Enterprise > your app > Agents > Add Agents > Custom agent via A2A > Add, paste the card into Agent card JSON (Register and manage A2A agents, agents using A2UI). Then add an authorization:

FieldValue
Client ID / secretFrom step 2
Scopeuseraccount
authorization URL
{AUTH_URL}
token URL
{INSTANCE}/oauth_token.do

One authorization belongs to one agent. To change an agent's card or authorization, delete and re-add the agent. Users should authorize in a browser not signed in to ServiceNow as an admin, or the agent acts as the admin.

8Try it

In Gemini Enterprise, open the agent, send "my laptop screen is cracked", click Authorize, sign in to ServiceNow as yourself, answer 2 (desktop). You should see your devices. From a terminal (answers as anonymous without a user token):

shell
uv run python scripts/chat.py --url {SERVICE_URL} --token "$(gcloud auth print-identity-token)"

Logs (Cloud Run logging, query language):

shell
gcloud logging read 'resource.type="cloud_run_revision" AND resource.labels.service_name="{SERVICE_NAME}"' --project {PROJECT_ID} --freshness=1h

shell · sign in once as a ServiceNow admin
uv run --group seed python seed/sn_seed.py login
uv run python scripts/sn_doctor.py --as {TEST_USER}

Deploy options

OptionUse it when
./scripts/deploy.sh (supported)Always, to start. Reads .env, checks the profile, deploys, grants Gemini Enterprise access. Idempotent.
gcloud run deploy --source . by handYou want to see or change every flag; the script is a readable wrapper around it.
adk deploy cloud_run, agents-cli deployNot a fit: this agent is a custom A2A server that passes the user's ServiceNow token through, which those tools don't set up.
TerraformOn the backlog (G2.4) for organizations that require infrastructure as code.
shell · the core of deploy.sh, by hand
gcloud run deploy {SERVICE_NAME} --source . --project {PROJECT_ID} --region {REGION} \
  --service-account hardware-agent@{PROJECT_ID}.iam.gserviceaccount.com \
  --no-allow-unauthenticated --memory 1Gi --concurrency 4 --timeout 300 --min-instances 1 \
  --set-env-vars "GOOGLE_CLOUD_PROJECT={PROJECT_ID},SN_INSTANCE_URL={INSTANCE},AGENT_ENGINE_ID=,SERVICE_URL={SERVICE_URL}"
gcloud run services add-iam-policy-binding {SERVICE_NAME} --project {PROJECT_ID} --region {REGION} \
  --member serviceAccount:service-{PROJECT_NUMBER}@gcp-sa-discoveryengine.iam.gserviceaccount.com --role roles/run.invoker

Use your ServiceNow's own options

The agent has no ServiceNow credentials of its own, so it never reads choice lists while running. Instead an admin checks the profile against the instance and imports a choice list when you want exactly your own options shown (for example only your hardware types). Sign in once with sn_seed.py login (step 9).

shell
uv run python scripts/sn_profile.py check
uv run python scripts/sn_profile.py choices subcategory --dependent hardware
uv run python scripts/sn_profile.py import-issues subcategory --dependent hardware --group personal

check confirms every field exists and every value the profile can write is a real choice. import-issues prints a ready-to-paste issues: list (labels and order from ServiceNow, your photo and urgency rules kept). Then map it onto the ticket:

yaml · write the chosen problem, or the device type, to your field
servicenow:
  ticket_fields:
    contact_type: self-service
    subcategory: "{device_value}"      # or "{issue_value}" after import-issues
  device_values: {laptop: cpu, desktop: cpu, monitor: monitor, keyboard: keyboard, mouse: mouse}

If ServiceNow refuses a configured field for a user, the ticket gets a note asking the service desk to set it.

ServiceNow roles

The agent acts as the signed-in user, so their roles decide what works. Measured with scripts/sn_doctor.py --matrix (temporary users per role set, every agent call, read back as admin) on a ServiceNow developer instance, 2026-09-30 (custom role column: 2026-10-01). u_hardware_requester alone, or itil alone, is enough for everything on this instance. With no roles, people can still report problems; what ServiceNow refuses, the agent handles: details go in the first note, changes become a note for the service desk (and the user is told), and equipment isn't matched to open tickets.

Licensing. itil is a fulfiller role and usually licensed per user. Granting it to every employee just for this agent is rarely right. For production, plan either no roles for requesters, or a small scripted REST API / Service Catalog item that sets ticket fields server-side. Check with your ServiceNow owner.

A custom role instead of itil: u_hardware_requester

Allows exactly what the agent does for a requester, on hardware tickets only: full details, urgency, status and cancel on their own tickets; notes and following on open ones; reading device records and their own group memberships. Only a session elevated to security_admin can create access rules, so it is a background script you run once:

  1. ServiceNow, as an admin: user menu > Elevate role > security_admin.
  2. System Definition > Scripts - Background: paste scripts/servicenow/create_hardware_requester_role.js, Run script. Safe to rerun; remove_hardware_requester_role.js undoes it.
shell · check, grant, measure
uv run python scripts/sn_custom_role.py status
uv run python scripts/sn_custom_role.py grant {TEST_USER}
uv run python scripts/sn_doctor.py --matrix --persona none --persona u_hardware_requester --persona itil

Check permissions

scripts/sn_doctor.py signs in as a ServiceNow admin, impersonates the user (no password), performs every call the agent makes and reads back what ServiceNow stored. It creates and deletes one test ticket per user; --read-only skips that.

shell
uv run --group seed python seed/sn_seed.py login
uv run python scripts/sn_doctor.py --as {TEST_USER}
uv run python scripts/sn_doctor.py --as {TEST_USER} --read-only
uv run python scripts/sn_doctor.py --matrix --markdown docs/role-matrix.md

Testing

Two layers. Unit and path tests run the tools against an in-memory ServiceNow (no network). Model-routing checks run the real agent and model on scripted conversations and check which tools it calls: typed tags, described equipment, a safety photo, "looks good" never changing the address, "ship it to my house", ticket updates, off-topic requests. Run them after changing the persona, the problem choices or the code.

shell
uv run --group seed pytest
uv run python evals/run.py
uv run python evals/run.py --repeat 3 safety     # one case, three times

Cases live in evals/cases.yaml; each turn lists the tools that must (or must not) be called, their arguments, and what the reply must show.

Troubleshooting

What you seeFix
deploy.sh stops: "Set ... in .env"Fill that variable (Configuration)
